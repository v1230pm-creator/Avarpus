Build the VMC Electronic Repair & Shop Management App as a REAL, FUNCTIONAL production-ready web/mobile-responsive application.

IMPORTANT:
- Do NOT create a static demo.
- Do NOT use fake/local demo data for the main business workflow.
- Use the existing authentication, database and server architecture already present in the project.

==================================================
1. AUTHENTICATION & USER ROLES
==================================================

Use the existing Register/Login system.

There should NOT be a public Staff Registration option.

Public registration is for the shop/dealer/owner account only.

Staff accounts must be created by the Dealer/Owner from inside the app.

Roles:
- Dealer / Owner
- Staff
- Technician

When a user logs in, the server must identify the account role automatically and load the correct dashboard and permissions.

Staff login must use the SAME Login page as Dealer/Owner.

Every staff member must have:
- Unique Staff ID
- Name
- Mobile number
- Email (if available)
- Role
- Active/Inactive status
- Created date
- Created by Dealer/Owner

Never trust the role sent by the frontend.
Role and permissions must be checked on the server.

==================================================

==================================================

Create a premium, clean and professional VMC Electronic dashboard.

Use the existing VMC Electronic visual identity.

Dashboard should show REAL server/database data:

Repair Overview:
- Today's Repairs
- Pending Repairs

- Total Customers

Financial Overview:

==================================================
3. REPAIR MODULE
==================================================

Repair section must contain exactly these 4 synchronized tabs:

1. RECEIVED
2. REPAIR
3. DELIVERED
4. AFTER-SALE SERVICE

All four tabs must work from the SAME repair/job record.

Do not create separate unrelated records when moving between tabs.

A repair job moves through the workflow:

RECEIVED
→ REPAIR
→ DELIVERED
→ AFTER-SALE SERVICE (only if customer returns after delivery)

==================================================
4. TAB 1 — RECEIVED
==================================================

Create a premium "Received Phone" workflow.

Button:
+ Receive Phone

When receiving a customer's device, allow Dealer/Owner/Staff/Technician (according to permissions) to enter:

Customer:
- Customer name
- Mobile number
- Alternate number
- Email (optional)
- Address (optional)

Device:
- Device type
- Brand
- Model
- IMEI 1
- IMEI 2
- Serial number
- Color
- Storage/RAM if applicable

Complaint:
- Customer complaint
- Detailed problem
- Device condition
- Accessories received
- Physical condition
- Existing damage

Intake:
- Date and time
- Expected delivery date
- Priority
- Estimated repair cost
- Advance payment
- Payment mode
- Notes

Device intake evidence:
- Device photos
- Damage photos
- Checklist
- Customer confirmation/signature

IMPORTANT:
Automatically record:

Received By:
- User ID
- User name
- User role
- Date/time

This must be immutable in the activity history.

Generate a unique Repair Job ID such as:
VMC-001, VMC-002, VMC-003...

After saving, show a complete Job Card/Repair Details page.

==================================================
5. RECEIVED → REPAIR
==================================================

When the received phone is accepted for repair, it moves to the REPAIR tab.

Do not duplicate the job.

Repair technician/staff assignment:

- Assigned technician
- Assigned by
- Assignment date/time
- Current repair status

Repair statuses:

- Received
- Diagnosing
- Repairing
- Testing
- Customer Approval Required
- Cannot Repair
- Waiting for Parts
- Repair Done
- Ready for Pickup

Allow technician/staff to add:
- Diagnosis
- Work performed
- Parts used
- Parts quantity
- Labour charge
- Other charges
- Repair notes
- Internal notes
- Before/after photos
- Testing result

==================================================
6. PARTS & INVENTORY
==================================================

When a part is consumed in a repair:

Automatically deduct the used quantity from inventory.

Store:
- Part name
- Part ID/SKU
- Quantity used
- Cost
- Selling price
- Used by
- Repair Job ID
- Date/time

Do not allow stock quantity to become negative unless Dealer/Owner explicitly allows it.

Track part warranty where applicable.

8. REPAIR DONE / TESTING
==================================================

==================================================
9. TAB 3 — DELIVERED
==================================================

The DELIVERED tab should contain phones ready for customer handover and completed handovers.

Clearly separate:

READY FOR PICKUP
and
DELIVERED

Customer delivery action must happen from the repair job details page.

Button:
"Hand Over / Deliver Device"

Before delivery show:

- Customer name
- Device
- Repair Job ID
- Repair work
- Parts replaced
- Final amount
- Advance
- Balance
- Payment status

When customer receives the phone:

Record:
- Delivered date/time
- Delivered by
- Staff/User ID
- Payment received
- Payment method
- Customer confirmation/signature or OTP where configured
- Final notes

Then automatically move the job to DELIVERED status.

Update all dashboard counters automatically.

==================================================
10. TAB 4 — AFTER-SALE SERVICE
==================================================

This is for customers whose repaired phone returns after delivery.

Example:
Phone was repaired and delivered.
After 5, 6, 7, 8 or 10 days the same problem occurs and customer returns.

Dealer/Staff must be able to open the original repair job and create an AFTER-SALE SERVICE / RETURN CASE.

Do NOT create a completely unrelated customer/device history.

Link the return to:
- Original Repair Job ID
- Customer
- Device
- Original repair
- Original technician
- Original delivery

Allow:
- Return date
- Return reason
- Customer complaint
- New diagnosis
- Photos
- New repair action
- Warranty status
- Free repair / chargeable repair
- Refund required
- Refund amount
- Refund method
- Replacement/redo repair
- Notes

==================================================
11. REFUND SYSTEM
==================================================

If the repair fails after delivery and the dealer decides to refund the customer:

Allow Dealer/Owner to record:

- Refund amount
- Refund reason
- Refund method
- Refund date
- Approved by
- Processed by
- Original payment reference
- Notes

Refund must appear in financial records.

Do NOT delete the original payment.

Instead create a linked refund transaction.

For Staff:
Refund/update actions requiring Dealer approval must show:

"Dealer Approval Required"

Dealer/Owner can approve or reject.

Every approval must be logged.
