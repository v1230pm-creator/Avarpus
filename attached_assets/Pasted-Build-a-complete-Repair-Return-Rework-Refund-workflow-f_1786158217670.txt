Build a complete "Repair Return / Rework / Refund" workflow for VMC Electronic.

REAL BUSINESS CASE:
Sometimes a customer's phone is repaired and delivered successfully, but after 5, 6, 7, 8 or 10 days the same customer returns because:
- The phone stopped working again
- The same problem came back
- A different problem appeared
- Repair was unsuccessful
- Customer requests refund
- Customer needs rework under the shop's warranty/repair policy

IMPORTANT:
Never delete or overwrite the original repair record.
Create a new Return/Rework event linked to the original Repair ID.

========================================
1. ADD "RETURN / REWORK" OPTION
========================================

In the Repair details screen add:

"Return / Rework"

When clicked, show:

- Original Repair ID
- Customer name
- Customer phone
- Device/model
- Original repair date
- Original delivery date
- Original repair/service
- Original amount charged
- Payment status
- Return date
- Days after delivery (calculate automatically)
- Reason for return
- Customer complaint
- Device condition on return
- Photos/videos if required
- Received by (automatically logged-in Staff/Dealer ID)

Return reason options:
- Same problem returned
- Phone stopped working
- Repair failed
- New problem
- Customer complaint
- Warranty rework
- Refund requested
- Other

========================================
2. TWO-STEP RETURN WORKFLOW
========================================

STEP 1 — RETURN INTAKE

When the phone comes back, staff/dealer records:
- Return date
- Customer complaint
- Device condition
- Photos
- Who received the device
- Original Repair ID

Generate a Return ID automatically.

Example:
Original Repair: VMC-005
Return: RET-VMC-005-01

STEP 2 — AFTER INSPECTION

After checking the phone, allow:
- Repair again / Rework
- Parts replacement
- No fault found
- Cannot repair
- Refund customer
- Partial refund
- Customer declined repair
- Other resolution

Record:
- Technician
- Diagnosis
- Work performed
- Parts used
- Parts cost
- Labour cost
- Total additional expense
- Amount to refund
- Amount already paid
- Final customer payable/refundable amount
- Notes
- Completion date

========================================
3. REFUND SYSTEM
========================================

If refund is required, show:

Original amount paid
Refund amount
Refund method:
- Cash
- UPI
- Bank transfer
- Card
- Other

Refund status:
- Pending approval
- Approved
- Paid
- Rejected

IMPORTANT:
Do NOT simply edit the original payment.

Create a separate financial transaction:
"REFUND"

Link it to:
- Original Repair ID
- Return ID
- Customer ID

Store:
- Refund amount
- Refund method
- Requested by
- Approved by
- Paid by
- Date/time
- Reason
- Reference/transaction number
- Audit log

The original payment must remain visible.

========================================
4. STAFF PERMISSION
========================================

STAFF can:
- Receive returned phone
- Create Return/Rework request
- Add complaint
- Upload photos
- Add diagnosis
- Add repair details
- Add parts used
- Prepare refund request

BUT:

STAFF CANNOT:
- Approve refund
- Change original payment
- Delete original repair
- Change original customer payment
- Finalize financial reversal
- Change previously approved financial records

When staff requests a refund or changes an important financial amount:

Show:
"Dealer/Owner approval required."

Create a pending approval request.

========================================
5. DEALER / OWNER
========================================

Dealer/Owner can:
- View all returned devices
- Approve/reject rework
- Approve/reject refund
- Change refund amount
- Approve financial adjustment
- Mark refund as paid
- Assign technician
- Reopen the repair
- Close the return case

Dealer/Owner does NOT need approval for their own actions.

========================================
6. APPROVAL SYSTEM
========================================

For staff-created refund/financial changes:

Create:

"Pending Approval"

Dealer dashboard notification:

"New Refund Approval Request"

Show:
- Customer
- Repair ID
- Return ID
- Original amount
- Requested refund
- Reason
- Staff name/ID
- Date
- Supporting photos/documents

Buttons:
APPROVE
REJECT

If rejected:
Require rejection reason.

========================================
7. REWORK WITHOUT REFUND
========================================

If dealer approves rework:

Change status to:

"Return Received"
→ "Inspection"
→ "Rework Approved"
→ "In Repair"
→ "Ready"
→ "Delivered"

Do NOT create a new unrelated customer repair.

Keep the original Repair ID linked with all return/rework history.

Example:

VMC-005
Original repair: ₹2,500
Delivered: 6 Aug

Customer returns: 14 Aug
Reason: Same problem returned

Return ID:
RET-VMC-005-01

Rework:
Speaker replaced

Parts cost:
₹300

Labour:
₹0

Customer payable:
₹0

Resolution:
Warranty Rework

========================================
8. PARTS AND INVENTORY
========================================

If parts are consumed during rework:

Automatically deduct those parts from inventory.

Record:
- Part name
- SKU
- Quantity
- Cost
- Technician
- Return ID
- Date/time

If refund is approved, do not automatically return parts to stock unless the actual part is physically returned.

========================================
9. CUSTOMER HISTORY
========================================

Customer profile should show:

Repair History
Return History
Rework History
Refund History

Example:

Customer: Rohit Mishra

Repair #VMC-005
₹2,500
Delivered: 6 Aug

Return #RET-VMC-005-01
Returned: 14 Aug
Reason: Same problem

Rework completed: 15 Aug
Refund: ₹0

All events should appear in chronological order.

========================================
10. AUDIT LOG — VERY IMPORTANT
========================================

Never permanently delete financial or repair history.

Track every important change:

- Who created it
- Who edited it
- Who requested approval
- Who approved/rejected
- Previous value
- New value
- Date/time
- Reason
- Device/Repair ID
- Return ID

Example:

Staff: Rahul (STF-012)
Requested refund: ₹2,500

Dealer: Vikash (DLR-001)
Approved refund: ₹2,500

Refund paid:
UPI
Transaction ID: XXXXX

========================================
11. DASHBOARD
========================================

Add dashboard cards:

Today's Returns
Pending Returns
Rework in Progress
Refund Pending Approval
Refunds Paid
Warranty Reworks
Repeat Customers

Add a "Returns & Rework" section in the Repairs module.

========================================
12. SEARCH AND FILTER
========================================

Allow searching by:

- Repair ID
- Return ID
- Customer name
- Mobile number
- Device
- Serial/IMEI if available
- Staff ID
- Technician
- Date
- Return reason
- Refund status

========================================
13. SECURITY
========================================

Permission must be checked on the SERVER/BACKEND, not only in the frontend.

Staff must not be able to bypass Dealer approval using API calls or direct requests.

Use the existing VMC Electronic role system:
- Dealer/Owner
- Staff
- Technician

Do not create a separate login system.

Do not add subscription/payment plans.

Do not break the existing registration, login, dashboard, repairs, customers, inventory or staff system.

Keep the existing premium VMC Electronic design and make the complete workflow responsive for mobile, tablet and desktop.

Before implementation, inspect the existing database/schema/API and integrate this feature with the current architecture instead of creating duplicate repair/customer/payment systems.
