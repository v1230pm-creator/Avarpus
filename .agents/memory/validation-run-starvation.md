---
name: Validation run starvation
description: Why the all-steps completion validation used to hang for 30+ minutes on the 4-core / 8 GB task container, how the step set is now shaped so one run finishes in ~5 minutes, and what still goes wrong (boot auto-start, supervisor port leak).
---

**Rule:** run every registered step in ONE `startValidationRun`; do not batch, and do not complete with `skip_validation_reason` citing batch run IDs (that workaround is retired). Measured 2026-09-22 with all seven dev workflows running: 24 steps pass in ~4.5–5 min wall, peak cgroup anon ~3.2–3.7 GB over a 1.7 GB idle baseline, minimum ~2.5 GB available, never more than two heavy node processes at once; the same set still passed in ~10 min when the box started with 0 MB available. The numbers and run IDs live in replit.md (Gotchas); re-measure and update them whenever a step is added.

**Why it used to starve:** the old registry ran the ~1.4 GB mobile `tsc` three times concurrently (`typecheck`, `workspace-typecheck`, `workspace-build` = typecheck && build), three admin browser suites each did a full vite build, and every heavy step was free to overlap — while ~3–5 GB of dev servers (Expo alone swings 0.4–1.8 GB) were resident. No swap and no OOM kill on this container: it thrashes instead (load 35–60, kernel time ≫ user time, a 3 s esbuild taking 85 s) until the harness gives up at its 30-minute poll budget with steps still RUNNING and code review TIMED_OUT.

**How it is shaped now (keep it this way):**
- Exclusive `flock /tmp/heavy-checks.lock` around anything running `tsc`, `vite build`, Metro export, Jest, Vitest or Chromium. Peak = baseline + the single largest step, not the sum. Light node scripts stay unlocked.
- api-server suites keep `flock /tmp/api-server-tests.lock`; steps needing both take api first, then heavy (`api-vitest`, `chat-relay-purge-e2e`). Same order everywhere or the two chains deadlock.
- Each expensive command runs once: root `build:artifacts` (no typecheck prefix) for `workspace-build`, `--workspace-concurrency=1` for the root typecheck (four parallel `tsc --build --force` on shared libs peaked higher and raced each other's output), one shared vite build for the admin browser suites, one avarpus-web `test` chain, one `vitest run` for the api suites. Sibling steps that re-run a command another step runs are the thing to refuse in review.
- Vitest steps carry `CI=1` (harness runs on a pty; the interactive reporter is useless there).
- Individual step footprints (tree PSS peak / wall, warm caches): root typecheck 1.36 GB / 45 s; build without typecheck 1.1 GB / 45 s (cold Metro export ~110 s); mobile Jest 1.3 GB / 30 s at `--maxWorkers=1` (1.7 GB / 17 s at 2 — memory is the scarce resource, so 1); api vitest 0.6 GB / 70 s; relay e2e 1.0 GB / 25 s; admin browser suites 0.8 GB / 40 s; each spawn-server api suite ~0.2 GB / 3 s.

**Measuring:** cgroup deltas are confounded by the Expo dev server's memory swings; measure a step's own tree (`/proc/<pid>/smaps_rollup` PSS of the descendants) or run it with the dev servers stopped. Sample `/sys/fs/cgroup/memory.stat` anon + `free -m` once a second from a `run_in_background` shell — a `nohup … &` sampler dies with the ShellExec that started it.

## Supervisor port leak (platform, 2026-09-22)
The workspace supervisor (`pid2`, the Node process that runs every workflow and validation step) keeps ~3 MB for every newly seen listening port for the life of the container — loopback or not, no HTTP contact needed, only that the socket lives long enough to be noticed (a 1 ms listen/close escaped; 1.5 s did not). Stock supertest opens one ephemeral server per `request(app)` call, so one api-vitest run (~500 requests) grew it by 1.4 GB, three runs took it from 0.2 GB to 4.2 GB, and it crashed: every workflow died and the in-flight validation run returned ERROR with no run ID; the restarted supervisor did not auto-start anything. The api suites now go through the `supertest` alias (vitest.config.ts → src/test-support/supertest.ts) that hands supertest one shared fixed-port server per test process: +92 MB per full run instead of +1.4 GB. Tell-tales: `ps -o rss -p $(pgrep -x pid2)` in the GBs and `free -m` available shrinking between runs while every step's own footprint is normal. Draining logs (RefreshAllLogs) does not release it; nothing in the repo can, only a container recycle. `ss` prints nothing in this container — list listeners from `/proc/net/tcp` (no `tcp6` file) instead.

## Boot-time auto-start
On a fresh task container every configured workflow — all validation steps as well as the dev servers — is started at boot. With the locks the backlog drains in ~5 min instead of thrashing indefinitely, but until then `flock /tmp/api-server-tests.lock` and `/tmp/heavy-checks.lock` are busy, so a by-hand test started immediately just queues. Check `ps aux | grep -E "[f]lock /tmp/"`; to clear the backlog, kill each validation step's process group (`ps -eo pid,pgid,args`, then `kill -TERM -- -<pgid>`) — never bracketless or generic `pkill -f "pnpm run build"` / `"pnpm run typecheck"` patterns: the api-server dev workflow's command line (`export NODE_ENV=development && pnpm run build && pnpm run start`) matches them, and an unbracketed pattern also matches the shell running the pkill.
