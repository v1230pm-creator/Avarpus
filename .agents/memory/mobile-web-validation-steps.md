---
name: Mobile & web validation steps
description: Which mobile/web test suites actually run at task completion, the shared heavy-checks lock that keeps tsc/Jest/vite builds from overlapping, and how to read a "No QueryClient set" failure in a layout test.
---

**Rules**
- `mobile-jest` runs the whole `artifacts/mobile/__tests__/**/*.test.tsx` glob at completion, so a new mobile test file is picked up automatically — but a red one now blocks completion. Keep `--maxWorkers=1`: 1.3 GB / ~30 s versus 1.7 GB / ~17 s at two workers, and memory, not time, is what the 8 GB task container runs out of.
- There is no separate mobile lock any more: the mobile `tsc` runs only inside `workspace-typecheck` (root `pnpm run typecheck`, `--workspace-concurrency=1`), and that step, `workspace-build`, `mobile-jest`, `web-checks`, `admin-browser`, `api-vitest` and the relay e2e all take the exclusive `flock /tmp/heavy-checks.lock`. Any new step that runs `tsc`, Jest, Vitest, a vite build or Chromium takes the same lock (see validation-run-starvation.md). The former `typecheck` (mobile tsc) step duplicated the workspace typecheck and was removed.
- `web-checks` = `CI=1 flock /tmp/heavy-checks.lock pnpm --filter @workspace/avarpus-web run test`, and the avarpus-web `test` script is now a catch-all: `test:scripts` (`node --test "scripts/test-*.mjs"`) then `test:dom` (one `vitest run --config vite.config.ts --environment jsdom --no-file-parallelism`, default include). A new `scripts/*.dom.test.tsx` or `scripts/test-*.mjs` is picked up with no registration; one vitest boot for all dom files (~12 s) replaced five. Do not go back to per-file `test:*` scripts — that shape is how `chats-safety.dom.test.tsx` sat unrun — and do not add a sibling validation step (the former `web-list-search` step was folded into the chain).
- The `test-registration-guard` step (`node scripts/src/check-test-registration.mjs`, see replit.md Gotchas) fails completion for any test file in any package that no `isValidation` step's command actually reaches. It resolves pnpm/flock/cd chains statically, so keep runner discovery readable: Vitest `test.include` must stay a literal string array, Jest `testMatch` must be set explicitly in the package config (a preset-supplied one is reported as unreadable), and a bare runner script is credited only for suite file names it mentions in string literals. A test file in a package with no runner step (e.g. `lib/*`) fails the guard until a catch-all runner script and step exist for it.
- `admin-browser` = `flock /tmp/heavy-checks.lock pnpm --filter @workspace/update-admin run test:browser`, which runs `scripts/run-browser-suites.mjs`: one production vite build into a private `tmp/browser-suites/<run>/public` directory reused by every `test-*-browser.mjs` suite through `UPDATE_ADMIN_BUILD_DIR` (`--strictPort` previews on fixed ports). A new browser suite is a new entry in that runner's list, not a new validation step.

**Why:** the dealer-portal-recovery mobile test sat red for weeks with "No QueryClient set, use QueryClientProvider to set one" because the suite was never a validation step; the tabs layout had gained the Chats-badge React Query hook chain (`useChatUnreadCount` → `useChatCapabilities`) and nobody ran the suite.

**How to apply:** when a mobile test that renders `app/(tabs)/_layout` (or anything mounting `PushNotificationsBridge`) fails with "No QueryClient set", it is harness drift, not a product bug — mount the component under a `QueryClientProvider` and stub the chat hooks at the `@workspace/api-client-react` boundary (idle `{ data: undefined }` queries), never by mocking the hook module or weakening the gate assertions. When validation piles up as RUNNING, the heavy steps are serialised by design and drain in ~5 min; look for a stale lock holder (`ps aux | grep -E "[f]lock /tmp/"`) before suspecting the steps.
